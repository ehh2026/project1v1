# Code Review — Bug & Robustness Findings

**Date:** 2026-06-21T19:48:42
**Scope:** Runtime tuning panel (`MainWindow.DeveloperTuning.partial.cs`, `Views/DeveloperTuningPanel.xaml.cs`), pin rendering — drawn (`Views/PinMarker.xaml.cs`) and composite image (`Views/CompositePinMarker.xaml.cs`, `MainWindow.CompositePins.partial.cs`), plus the placement/layout/navigation glue that those features touch.

Severity legend: **HIGH** = user-visible breakage / corrupt state, **MEDIUM** = wrong-in-edge-cases or latent, **LOW** = cleanliness / robustness.

## HIGH

### H1. Applying tuning while zoomed into a cluster corrupts the view state
**File:** `MainWindow.DeveloperTuning.partial.cs` — `CanRunTuningAction` (180) and `RecreateAllMarkersAsync` (169)

`CanRunTuningAction` blocks Apply/Save/Reload only while *animating* or in *edit mode*. It does **not** block while the user is zoomed into a cluster (`_currentZoomedCluster != null`, back button visible, viewport zoomed).

When a size/threshold change forces `needsRecreate`, `RecreateAllMarkersAsync` does:

```csharp
_extensionLineRenderer.Clear();
_overrideStore.ClearAll();
ClearAllMarkers();
_clusters = await _contentLoader.LoadClustersAsync();
AddClustersToMap(_clusters);   // rebuilds the FULL-MAP cluster view
```

But it never resets `_currentZoomedCluster`, the navigation stack, `BackButton`, or the zoomed viewport. Result: the full-map cluster markers are rebuilt and positioned against a still-zoomed viewport, while `_currentZoomedCluster` and the nav stack still claim you're zoomed in. The app is left in a contradictory half-state (e.g., Back button does the wrong thing, edit-layout key resolution is wrong).

**Fix options:**
- Add a guard to `CanRunTuningAction` that rejects recreate-class changes while `_currentZoomedCluster != null` (simplest), **or**
- Have `RecreateAllMarkersAsync` first unwind zoom state (`_currentZoomedCluster = null`, clear nav stack, hide Back, reset viewport to full map) before rebuilding.

## MEDIUM

### M2. Reload-from-disk bypasses the panel's input validation
**File:** `MainWindow.DeveloperTuning.partial.cs` — `OnReloadTuningFromDisk` (55) / `CreateTuningArgs` (203)

The UI Apply path is validated by `DeveloperTuningPanel.TryBuildEventArgs` (positive sizes, finite numbers, etc.). The reload path constructs `TuningPanelEventArgs` **directly** from the loaded file and calls `ApplyTuningAsync` with no validation:

```csharp
var fresh = _configService.Load(_configPath);
await ApplyTuningAsync(CreateTuningArgs(fresh));   // no positivity/finite checks
```

A hand-edited or corrupt `visual-config.json` (e.g., `LocationMarkerSize: 0` or negative `ClusterMarkerSize`) is applied straight onto `_visualConfig` and pushed into marker creation. Recommend running the same validation used by the panel (or clamping) before applying reloaded values.

### M3. Angle comparison reuses a *pixel* tolerance as a *degree* tolerance
**File:** `Services/CompositePinPlacementPolicy.cs` — `ShouldRepositionOnly` (42)

```csharp
public static bool ShouldRepositionOnly(..., double tolerancePx = 0.5)
...
if (AngleDifferenceDeg(angleDeg, existingPlan.TargetAngleDeg) > tolerancePx)  // degrees vs "px"
    return false;
...
if (Math.Abs(lengthPx - existingPlan.TargetLengthPx) > tolerancePx)          // px — correct
```

The same `tolerancePx` value (0.5) is used both as a length tolerance in pixels and as an angle tolerance in degrees. 0.5° happens to be reasonable, but the unit conflation is a latent bug: tuning the pixel tolerance silently changes angular sensitivity (and vice-versa). Split into `toleranceDeg` and `tolerancePx` with independent defaults.

### M4. `UpdateMarkerPositions` can orphan composite-pin guide lines in edit mode
**Files:** `MainWindow.xaml.cs` `UpdateMarkerPositions` (441→485) → `ExtensionLineRenderer.Apply` (81) + `TryApplyCompositePinMarker` (169)

`UpdateMarkerPositions` passes `TryApplyCompositePinMarker` as the applier. In edit mode that method *adds* an extension line on success:

```csharp
if (ok && _layoutEditor.IsEditMode)
    _extensionLineRenderer.AddLine(marker, originalScreenPos, extendedScreenPos);
```

But back in `ExtensionLineRenderer.Apply`, when the applier returns true the renderer then removes the marker’s tracking entries:

```csharp
_markerToLine.Remove(marker);
_markerToPinLines.Remove(marker);   // dictionary entries removed, but the Line visuals stay in _lines/_canvas
```

The `Line` objects remain on the canvas and in `_lines`, but are no longer reachable via `_markerToLine`/`_markerToPinLines` — so `MoveLineEndpoint`/`SetLineZIndex` can’t find them, and they only get cleared on the next full `Clear()`. Outside edit mode this is a harmless no-op (no line was added), so the bug is confined to the edit-mode + composite + WithExtensions path. Recommend not adding the line in `TryApplyCompositePinMarker` when the caller (`Apply`) is the one managing line lifecycle, or have `Apply` fully remove rather than just untrack.

### M5. Per-tick full rebuild of the composite marker during drag
**File:** `MainWindow.LayoutEditor.partial.cs` — `OnMarkerDragMove` (656) → `ApplyCompositePinToMarker`

Composite drag deliberately bypasses the `ShouldRepositionOnly` fast-path (“always full reapply — angle/length change each tick”). Every mouse-move tick allocates a brand-new `CompositePinMarker`, re-runs `BuildPlan`, reloads/reapplies layers, and re-subscribes `ShaftOverrideRequested`. It’s functionally correct and not a leak, but it’s heavy allocation churn on the UI thread during drag. Consider a lightweight reposition+restretch path that mutates the existing marker when only length changes, falling back to full rebuild when the assignment changes.

**File:** `MainWindow.Navigation.partial.cs` (324) — `previousState` is popped purely to decrement the stack; the zoom-out target is always `CreateFullMapView(...)`. Both flags are pure render-time options consumed in `SetCompositeImages`; neither changes the geometry of a render plan, so clearing the whole plan cache (and forcing rebuilds) is unnecessary work. ### L10. `async void` event handlers can swallow/escape exceptions
**File:** `MainWindow.DeveloperTuning.partial.cs` — `OnApplyTuning` (32), `OnReloadTuningFromDisk` (55). The bodies are guarded (`ApplyTuningAsync` and the reload `try/catch`), so this is currently safe, but any future early `await` added before the `try` would throw on the UI dispatcher with no handler. Keep all awaited work inside the try, or wrap the handler bodies.

### L11. Repeated unused `using` directives across the `MainWindow.*.partial.cs` files
Every partial re-imports `System.Windows.Media.Animation`, `…Effects`, `…Shapes`, `System.Windows.Controls.Primitives`, etc., most unused per-file. Minor noise; a `dotnet format`/IDE “remove unused usings” pass would clean it up.

# Follow-up (2026-06-21, second pass) — composite toggle desync, layout coverage, drag "stub"

## H12. Tuning changes don't replay the active manual layout → composite toggle "desyncs" until you enter Edit Layout
**File:** `MainWindow.DeveloperTuning.partial.cs` — `ApplyTuningAsync` (142–152)

The non-recreate branch ends with a bare `UpdateMarkerPositions()`:

```csharp
else
{
    if (turningCompositeOff || (compositePlanChanged && newCanUseComposite))
        RestoreBaseMarkerVisuals();

    UpdateMarkerPositions();   // recomputes AUTO placement only — never replays the manual layout
}
```

`UpdateMarkerPositions()` recomputes auto-placement from the orchestrator; it does **not** replay an active manual layout (that is a separate `ApplyManualLayout` / `TryApplyFullMapManualLayout` step). So when a manual layout is active and the user toggles composite on/off:

- Saved head/endpoint positions are discarded; markers snap to auto-placement.
- Entering Edit Layout calls `OnEditLayoutButtonClick → ApplyManualLayout`, which rebuilds both composite **and** drawn pins at the saved positions — so it appears to "fix itself" in edit mode. This is exactly the reported symptom.

Note the inconsistency that makes it confusing: the **recreate** branch (`RecreateAllMarkersAsync → AddClustersToMap`) *does* call `TryApplyFullMapManualLayout()`, so size/threshold changes re-apply the full-map layout — but the **toggle** (non-recreate) branch does not re-apply anything. That's why "some tuning changes stick and the composite toggle doesn't."

**Fix shape** — after a tuning change, mirror `ExitEditMode`'s replay logic instead of a bare `UpdateMarkerPositions()`:

```csharp
private void ReapplyAfterTuningChange()
{
    if (_layoutEditor.IsManualLayoutActive && _layoutEditor.CurrentLayoutKey != null)
    {
        var layout = _layoutEditor.TryLoad(_layoutEditor.CurrentLayoutKey);
        if (layout != null) { ApplyManualLayout(layout); return; }
    }

    if (_currentZoomedCluster != null)
        ShowZoomedView(_currentZoomedCluster);   // cluster-zoomed replay (see below)
    else
    {
        UpdateMarkerPositions();
        TryApplyFullMapManualLayout();            // full-map replay
    }
}
```

### Can auto-replay also cover the cluster-zoomed view? — Yes.
There is already precedent: `OnDeleteLayoutButtonClick` recovers the zoomed view with `ShowZoomedView(_currentZoomedCluster)` (`MainWindow.LayoutEditor.partial.cs:446-449`). `ShowZoomedView` regenerates the cluster layout key, loads any saved cluster layout, and applies it via `ApplyManualLayout`. So the replay helper above can route the `_currentZoomedCluster != null` case through `ShowZoomedView(_currentZoomedCluster)` and the cluster layout will come back after a toggle, not just the full-map layout. (For a pure size/threshold change that hits the recreate path, `RecreateAllMarkersAsync` should likewise unwind/redisplay the zoomed cluster rather than rebuilding the full-map cluster view — see **H1**.)

## Q2 answer — manual layouts DO apply to both drawn and composite pins, and the tip is correctly fixed by the Excel data (verified)
- **Tip (origin) is always re-derived from Excel coords**, never from the saved layout: `ApplyManualLayout` builds `sourceCoords` from `Location.PixelX/PixelY`, and `CompositePinApplicationService.BuildApplyInstructions` sets `OriginalScreen = viewport.SourceToScreen(source.PixelX, source.PixelY, …)` (`CompositePinApplicationService.cs:120-124`). The stored origin is only a no-viewport fallback. → tips are not editable. ✔
- **Head (endpoint) is the editable part** — `ExtendedScreen` comes from the saved `SourceExtendedX/Y` (or angle/length) (`:131-146`). ✔
- **Both render modes are handled** in `ApplyManualLayout` (`MainWindow.LayoutEditor.partial.cs:549-606`): composite via cached plan → `ApplyRenderPlanToMarker` or `TryApplyCompositePinMarker`; drawn-with-moved-head → extension line *is* the shaft (tip→head) with the pin's own shaft hidden; drawn-unmoved → normal pin centered on its map location with its own shaft. ✔
- **Drag keeps the tip fixed for both**: composite drag recomputes `originalPos` from `PixelX/PixelY` each tick (`OnMarkerDragMove:672`); drawn drag only moves the line endpoint while `MoveLineEndpoint` keeps `X1,Y1` (the tip) fixed. ✔

So the intended model is fully implemented; the *appearance* that composite pins ignore layouts is a side-effect of **H12** (no replay after toggle).

## H13. Composite-pin drag shows a short "stub" head + small shaft instead of reaching the cursor
**Files:** `Services/PinPartPlacementCalculator.cs` (89–110), `MainWindow.LayoutEditor.partial.cs` `OnMarkerDragMove` (668–697)

In `NearestFit` mode (the configured default) the shaft stretch is clamped:

```csharp
var minStretch = Math.Min(config.MinStretchFactor, config.MaxStretchFactor); // 0.75
var maxStretch = Math.Max(config.MinStretchFactor, config.MaxStretchFactor); // 1.35
if (appliedStretch > maxStretch) { appliedStretch = maxStretch; isStretchClamped = true; }
```

(config: `MinStretchFactor 0.75`, `MaxStretchFactor 1.35`.) So the rendered composite shaft can only reach `1.35 × nativeLength`. When the user drags the head farther than that, the composite is rebuilt every tick with the **head clamped** to the max stretch distance from the fixed tip, so it renders as a short "stub" near the map anchor. Meanwhile `OnMarkerDragMove` also calls `_extensionLineRenderer.MoveLineEndpoint(_draggedMarker, mousePos)`, drawing the **drag-guide line all the way to the cursor**. The result is the reported visual: a small stub pin + a thin guide line, the two endpoints diverging as you drag out.

Why it looks correct on exit: the **saved** endpoint is the true cursor position (`GetMarkerEndpoint` returns the guide-line endpoint), the guide line is cleared, and the best-fit scorer re-selects a longer native shaft for the final length — so unless the final drop still exceeds `1.35×` the longest available shaft, the replayed composite reaches the saved head and reads correctly.

This is a genuine UX/correctness gap: **during drag the rendered composite head and the guide-line endpoint represent different positions.** Options:
- Position the composite during drag from the *clamped* plan but keep the guide line as the source of truth, and visibly snap/resolve on drop (document the clamp), or
- Use a longer-shaft selection / allow temporary over-stretch during drag so the rendered head tracks the cursor, or
- Surface the stretch clamp (e.g., expose `MaxStretchFactor` in the tuning panel and/or warn via `IsStretchClamped`) so long pins aren't silently truncated.

At minimum, the divergence between guide endpoint and rendered head during drag should be reconciled so the user isn't dragging a head that doesn't track the cursor.

> **Note (mode):** H13 is **composite-mode only** — the stretch clamp lives in `PinPartPlacementCalculator` and never runs for drawn pins. A "stub moving during drag" seen in **drawn** mode is a *different* bug — see H14.

## H14. Drawn-pin drag drags the whole pin glyph (head + built-in stub shaft) with no connecting shaft — drawn-mode "stub" during drag
**File:** `MainWindow.LayoutEditor.partial.cs` — `OnMarkerDragMove`, legacy/drawn branch (700–744)

Drawn pins (`marker.Content is PinMarker`) fall through to the legacy drag branch, which only repositions the marker and — *if a line already exists* — moves that line's endpoint:

```csharp
var markerSize = _visualConfig.LocationMarkerSize;      // 16, NOT the pin's real size
var newX = currentPosition.X - (markerSize / 2);        // center on cursor by 16px box
var newY = currentPosition.Y - (markerSize / 2);
...
Canvas.SetLeft(_draggedMarker, newX);
Canvas.SetTop(_draggedMarker, newY);

if (_extensionLineRenderer.HasLine(_draggedMarker))      // only updates an EXISTING line
    _extensionLineRenderer.MoveLineEndpoint(_draggedMarker, new Point(newX + markerSize/2, newY + markerSize/2));
else
    LogDragDebug("... No line found ...");                // <-- no line is created during drag
```

Two concrete problems, both visible in **drawn mode**:

1. **No connecting shaft while dragging a non-extended pin.** If the pin had its head sitting on its map tip (head not yet moved → `RequiresExtensionLine` was false → no extension line, and the pin's *own* built-in shaft is visible), then `HasLine` is false, so no line is created on the fly and the built-in shaft is never hidden. The entire `PinMarker` glyph — head + short built-in shaft — slides under the cursor with nothing tethering it to the fixed map tip. This is the "whole stub pin head and small shaft moving" you observed. (Composite drag avoids this by rebuilding the pin each tick so the shaft stretches from the fixed tip.)

2. **Head/endpoint offset uses the wrong anchor.** Positioning centers on `LocationMarkerSize` (16px), but a `PinMarker`'s head/connection point is `GetConnectionPoint() = (Width/2, PinBall.Height/2)` and its `Width/Height` come from `PinMarkerConfig` (ball+shaft), not 16. So even when a line *does* exist, the head doesn't sit on the line endpoint during drag, and the line endpoint is computed from the 16px box center rather than the head — guide and head diverge.

**Why it self-corrects on exit:** `ExitEditMode`/save → `ApplyManualLayout` re-derives the drawn layout — moved head → `RequiresExtensionLine` true → extension line becomes the shaft, the pin's built-in shaft is hidden (`SetShaftVisible(false)` via `AnchorExtendedMarker`), head anchored on the endpoint, tip re-projected from Excel. Hence "the tip and shaft were in the right place" afterward.

**Fix shape:** during drawn-pin drag, mirror the composite path — ensure an extension line exists (create it on first move from the fixed tip), hide the pin's built-in shaft, and anchor/position by the pin's connection point rather than the 16px box. This is the same defect the drawn-pin-model-separation work targets (`docs/exec-plans/active/drawn-pin-model-separation-plan.md`): edited drawn pins shouldn't depend on toggling a built-in vertical shaft.
